# Track Access Security

This document describes how CMC protects uploaded track audio, how purchase ownership is granted, and how the app prevents users from accessing full tracks unless the server has confirmed that they are allowed to do so.

The central rule is:

> Browser state is never trusted for track access. Full playback and downloads are granted only by server-side checks against the current authenticated user and the `TrackOwner` table.

## Storage Model

Track audio is stored outside the browser-accessible app bundle, currently in S3-compatible object storage configured through:

- `S3_ACCESS_ID`
- `S3_APP_ACCESS_KEY`
- `S3_BUCKET_NAME`
- `S3_REGION`
- `S3_KEY_PREFIX`

The browser does not receive S3 credentials. It only receives short-lived signed URLs generated by server code.

Production and non-production storage must remain separated by different buckets or by mandatory environment prefixes. The intended environment split is documented in `ENVIRONMENT_MATRIX.md`.

## Public Catalogue Data

The public catalogue can expose track metadata for browsing, searching, and detail pages, but only for tracks matching the public publication predicate in `lib/server/tracks-core.mjs`.

Public metadata can include title, composer, key, instrumentation, price, uploader display context, preview metadata, and comment/request counts. It must not include secret storage credentials or grant full audio access.

## Preview Access

Anonymous and signed-in visitors may request a sample preview through:

```text
GET /api/tracks/[trackId]/signed-url?mode=sample
```

The sample path is deliberately separate from full-track access:

1. The route only loads tracks that are public and published.
2. It rate-limits sample URL issuance.
3. It uses `Track.previewFileName` via `getSampleAudioKey()` in `lib/track-audio-access.mjs`.
4. It does not sign the full uploaded object for real uploads.
5. If a real uploaded track has no explicit preview asset, the route returns `404 Preview unavailable`.

Synthetic demo fixtures may use a time fragment for testing/demo playback when synthetic fixtures are explicitly enabled. Production must not rely on synthetic fixtures and must keep `CMC_ENABLE_SYNTHETIC_FIXTURES` unset or false.

## Full Playback And Downloads

Full playback and downloads use the same protected endpoint with different modes:

```text
GET /api/tracks/[trackId]/signed-url?mode=full
GET /api/tracks/[trackId]/signed-url?mode=download
```

Both modes require:

1. A valid authenticated session from `requireRouteCurrentUser()`.
2. Method and query validation through the route validation layer.
3. User-aware rate limiting.
4. A server-side ownership decision from `canAccessFullTrack()` in `lib/server/ownership.js`.

`canAccessFullTrack()` grants access only when one of these conditions is true:

- the current user uploaded the track, or
- the current user has a matching `TrackOwner` row for the track.

If neither condition is true, the route returns `403 Track access denied`, records a `track_access.denied` audit event, and does not issue a signed URL.

When access is allowed, the server signs the original full track object for a short period using `getSignedTrackUrl()` in `lib/server/s3`. Download mode also passes the safe download filename. The signed URL is temporary and is never treated as a permanent ownership credential.

## Purchase And Ownership Granting

Purchasing is intended to be server-authoritative:

1. The buyer selects tracks in the app.
2. The server creates a pending `Order` and `OrderItem` records after validating that the tracks exist, are purchasable, have valid prices, and are not already owned.
3. Stripe Checkout handles payment.
4. Ownership is granted only after a verified paid checkout event is processed.
5. `fulfilPaidOrder()` in `lib/server/orders.js` creates or reuses `TrackOwner` rows inside a database transaction.
6. Ownership grants are idempotent through the unique `trackId_userId` relation.
7. Each ownership grant records an `ownership.granted` audit event.

The production posture must keep direct simulated fulfilment disabled with `ALLOW_SIMULATED_PURCHASES` unset or false. Simulated purchase flows are for controlled local/E2E testing only.

## Comments And Purchased-Only Community Actions

Commenting is also ownership-gated. The comments endpoint in `app/api/profile/route.js` checks the current authenticated user and then requires a matching `TrackOwner` row before creating a comment.

This means a signed-in user who has not purchased a track can browse the metadata and preview the approved sample, but cannot leave owner-only comments on that track.

Requests are signed-in community actions, not proof of track ownership. They should not grant audio access.

## Review Access

Review mode is separate from customer ownership:

```text
GET /api/tracks/[trackId]/signed-url?mode=review
```

Review URLs are only issued to users who pass the support/admin permission check in `canAccessSupportSurface()`. Denials are audited as track access denials. Review access exists for moderation and support workflows, not for ordinary catalogue users.

## Frontend Responsibilities

The frontend may improve user experience by showing or hiding buttons based on known ownership state, but that state is advisory only.

Examples:

- owned users can see full playback/download actions;
- non-owners see preview and purchase actions;
- uploaded-by-viewer tracks can use full playback for the uploader;
- profile downloads link to canonical catalogue track details.

These UI states do not grant authority. A user editing JavaScript, modifying local component props, or calling the API directly still has to pass the server-side signed URL checks.

## Auditability

The track access path records durable audit events for security-sensitive decisions:

- `track_access.denied` when a user tries to access a full, download, or review URL without permission;
- `track_access.signed_url_issued` when an owned, downloaded, or review URL is issued;
- `ownership.granted` when a paid order grants ownership;
- `comment.created` when an owner comments on a purchased track.

Operational monitoring guidance for these events lives in `OPERATIONS_RUNBOOKS.md`.

Useful incident signals include:

- repeated `track_access.denied` events for one actor or one track;
- unexpected spikes in `track_access.signed_url_issued`;
- ownership grants without matching payment events;
- production deployments with simulated purchases or synthetic fixtures enabled.

## Test Coverage

The current security posture is covered by focused unit and browser tests, including:

- `test/track-audio-access.test.mjs`
- `test/e2e/api-auth-gates.spec.js`
- `test/e2e/authenticated-smoke.spec.js`
- `test/e2e/checkout-flow.spec.js`
- `test/e2e/public-smoke.spec.js`

Important regressions these tests should continue to catch:

- anonymous users cannot request full track URLs;
- signed-in non-owners cannot request full, download, or review URLs;
- sample URLs do not sign the original full uploaded object for real uploads;
- purchased tracks appear in the buyer profile after verified checkout;
- owner comments require a purchased track;
- support/admin review access is separated from customer ownership.

## Known Limits

This model protects access to CMC-hosted full audio. It cannot technically prevent a legitimate buyer from copying or sharing a file after they have downloaded it.

Mitigations for later phases may include:

- terms that clearly prohibit redistribution;
- account-level download history and abuse monitoring;
- watermarking or buyer-specific audio tagging for downloads;
- streaming-first subscription access for future mobile/native apps;
- rate limits and anomaly alerts around repeat download behaviour.

These mitigations reduce abuse and improve traceability, but they do not replace the server-side ownership checks described above.

## Release Checklist

Before releasing changes that touch track access, confirm:

- full/download/review modes still require server authentication;
- `canAccessFullTrack()` is still the authority for customer full-track access;
- sample mode signs only explicit preview assets for real uploads;
- S3 credentials are never exposed to client code;
- signed URL expiries remain short;
- production has simulated purchases and synthetic fixtures disabled;
- ownership is granted only from verified paid checkout processing;
- audit events are still emitted for denied and issued track access;
- the focused track access and E2E tests pass in CI.
